# Phase 1 · Garbage collection defaults

## Goal

Change the **recommended / default JVM launch flags** a Victus instance runs under from the legacy
**Aikar/G1** set to **Generational ZGC** (Java 21+), so a running server stops losing ticks to
stop-the-world GC pauses — **without changing a single gameplay outcome or any plugin-observable
behaviour.** The garbage collector is invisible to game logic and to the Bukkit/Spigot/Paper API, so
this delta is 100% plugin-compatible in the default (`single`) path by construction: it is a change
to the *launch command*, not to server code.

The honest, load-bearing distinction up front, because this area is the easiest to mis-state:

- **The collector is chosen by JVM launch flags, not by the server at runtime.** You cannot switch
  from G1 to ZGC after the JVM has started. So Victus's *code* delta here is deliberately tiny — an
  **informational GC advisor** that reads the active collector at boot and **warns on mismatch** with
  `optimizations.gc.profile`. It **never** sets or changes a JVM flag. This mirrors the
  `warn-if-no-jvm-string-dedup` pattern in [`06-memory.md`](06-memory.md) exactly.
- **The real deliverable is the flag set**, owned by the launch layer: `scripts/dev-env.sh` (dev
  reference, already carries the flags) and the **Victus Wings start-script template** (production,
  the control plane that actually spawns each instance — see ARCHITECTURE §5). This spec pins that
  flag set precisely and formalizes the advisor that polices it.

So Victus's delta over Paper 26.1 is **policy + a boot-time check**, not a new subsystem:

1. Recommend/default **Generational ZGC** (`-XX:+UseZGC -XX:+ZGenerational`) fleet-wide, replacing
   Aikar's G1 flags, for sub-millisecond pauses vs G1's **~35 ms average / ~180 ms p99** (illustrative
   — see Honest expected gain) — pauses long enough to blow the 50 ms tick budget and cause visibly
   missed ticks.
2. Pin the **exact recommended start flags** (including `AlwaysPreTouch`, `PerfDisableSharedMem`, an
   OS-headroom rule, and an explicit "do **not** mix in old G1/Aikar flags" rule).
3. Ship the **GC advisor**: read the running collector at boot, warn once if it does not match
   `optimizations.gc.profile`, and warn if ZGC is active but **generational mode is off** (which
   quietly loses throughput). Surface the same thing as a `/victus doctor` remediation.

This is a **deliberate migration off the current Victus fleet Aikar tuning** (see the fleet
`game-server JVM tuning` and infra memory) and must be **validated on a pilot node first** — it is
tracked as a known risk in [`../ROADMAP.md`](../ROADMAP.md) ("ZGC default switch").

## Upstream baseline (what Paper 26.1 already provides)

**We must not claim the JVM's or Paper's work as ours.** Honest inventory:

- **Paper ships no in-jar collector opinion.** The GC is entirely a function of the JVM launch flags;
  Paper's jar does not and cannot pick the collector. What Paper *does* provide is **guidance**: its
  documented/recommended start flags have long been **Aikar's flags** (a G1GC tuning set), and its
  `start`-script convention includes the `-Dusing.aikars.flags=…` marker. Out of the box, an operator
  following Paper's docs runs **G1 with Aikar tuning** — that is the baseline Victus's default
  replaces. `TODO(verify)` whether Paper 26.1's bundled/recommended flags still point at the classic
  Aikar G1 set or have themselves moved toward ZGC by 26.1.
- **The JDK provides the collectors.** OpenJDK/HotSpot 21+ ships **G1** (default), **Parallel**,
  **Serial**, **Shenandoah**, and **ZGC**. **Generational ZGC** landed in **JDK 21** (JEP 439) and is
  enabled with `-XX:+UseZGC -XX:+ZGenerational`. In **JDK 23** (JEP 474) generational became the
  **default** for `-XX:+UseZGC` and `-XX:+ZGenerational` was **deprecated** (non-generational ZGC
  deprecated for removal). So the exact flag spelling depends on the target JDK — see Design.
  `TODO(verify)` the exact JDK Paper 26.1 requires/ships against; CONTRIBUTING notes local
  `java 21.0.3`, but "26.1 may require newer".
- **`-XX:+UseStringDeduplication` is JDK-provided and decoupled from G1.** Originally G1-only, it was
  made available to all collectors (ZGC/Shenandoah included) in **JDK 18+**, so it rides the same
  launch line as Generational ZGC. It is **owned by the memory spec** ([`06-memory.md`](06-memory.md)
  item 4), not re-specified here; this spec only keeps the recommended flag line consistent with it.
- **`gc.profile` already exists in the schema.** `VICTUS-CONFIG.md` defines
  `optimizations.gc.profile: zgc-generational` and states it is **informational** ("the JVM's
  collector is set by launch flags, not by the server at runtime; the engine reads the active GC and
  warns on mismatch"), and `scripts/dev-env.sh` already carries the reference flag block. This spec
  **pins the semantics** of both and adds the advisor + two sub-flags — it does not invent the key.
- **Paper does not measure/warn on your GC.** There is no upstream Paper feature that reads the active
  collector and tells the operator it is misconfigured. That advisory surface is genuinely new Victus
  code (small), wired into the same boot-warning + `/victus doctor` path as the memory spec's item 4.

So there is **no upstream Paper option to bind** here (unlike redstone/chunks) and **no new game
subsystem to write** — the collector choice lives in the launch flags, and the only new *code* is the
boot-time advisor. The value is in getting the flags right fleet-wide and policing them.

## Design / patch plan

Two pieces of work: the **flag set** (launch layer, the real change) and a small **GC advisor**
(server patch, the check). Neither touches the tick loop or any game logic.

### 1. Recommended launch flags — Generational ZGC (launch layer, the delta)

These live in `scripts/dev-env.sh` (dev reference — already present) and, for production, the
**Victus Wings start-script template** per plan size. The exact recommended set:

```bash
java \
  -Xms<N>G -Xmx<N>G \
  -XX:+UseZGC -XX:+ZGenerational \
  -XX:+AlwaysPreTouch \
  -XX:+PerfDisableSharedMem \
  -XX:+UseStringDeduplication \
  -Dusing.aikars.flags=false \
  -jar victus-engine.jar --nogui
```

Rationale + hard rules, each grounded:

- **`-XX:+UseZGC -XX:+ZGenerational` — the collector.** Concurrent, region-based, pauses in the
  **sub-millisecond** range **independent of heap size**. `ZGenerational` **must be present** on
  JDK 21/22: single-generation ZGC collects the whole heap every cycle and **loses meaningful
  throughput** vs the generational form — running plain ZGC would forfeit much of the point. On
  **JDK 23+** generational is the default and `-XX:+ZGenerational` is **deprecated** (harmless but may
  print a deprecation warning); the advisor treats "ZGC active + generational on" as correct
  regardless of how it was enabled. `TODO(verify)` the flag's status on the exact target JDK and drop
  the explicit flag if the fleet standardizes on JDK 23+.
- **Set `-Xms` == `-Xmx`.** A fixed heap avoids resize churn and pairs with `AlwaysPreTouch`.
- **`-XX:+AlwaysPreTouch`.** Faults in every heap page at startup so there are no first-touch
  page-fault stalls mid-tick — steadier per-tick latency. Cost: **slower startup** proportional to
  heap size, and the process commits the full `-Xmx` in RSS up front (factor into node density). A
  server boots once, so this is the right trade for hosting.
- **`-XX:+PerfDisableSharedMem`.** Disables the `/tmp/hsperfdata_*` perf-counter file, removing a
  known source of GC/safepoint hiccups caused by disk I/O to `/tmp`. **Caveat:** it hides the JVM from
  `jstat`/attach-by-file tooling — acceptable because Victus reads metrics via MXBeans/Prometheus, not
  `jstat` (ARCHITECTURE §5). Carried over from Aikar's set (it is collector-agnostic).
- **`-XX:+UseStringDeduplication`.** Complementary, **owned by [`06-memory.md`](06-memory.md)**; kept
  on the same line so the two specs agree. Zero tick cost (background GC-thread work).
- **`-Dusing.aikars.flags=false`.** Suppresses Paper's Aikar-flags marker message; a signal that we
  are **not** on Aikar tuning anymore.
- **Leave ~1–1.5 GB of RAM for the OS + off-heap.** Size `-Xmx` at roughly *(container RAM − 1 to
  1.5 GB)*, not the full box. ZGC has higher off-heap/mapped-memory overhead than G1 (address-space
  reservation, colored-pointer machinery), and Metaspace, thread stacks, and Netty **direct buffers**
  all live outside `-Xmx`. Under-provisioning headroom risks native-OOM/OOM-killer, which no GC flag
  fixes.
- **Do NOT mix in old G1/Aikar flags.** Aikar's set is **G1-specific**
  (`-XX:+UseG1GC`, `-XX:G1NewSizePercent`, `-XX:G1MaxNewSizePercent`, `-XX:G1HeapRegionSize`,
  `-XX:G1ReservePercent`, `-XX:G1HeapWastePercent`, `-XX:G1MixedGCCountTarget`,
  `-XX:InitiatingHeapOccupancyPercent`, `-XX:G1MixedGCLiveThresholdPercent`,
  `-XX:G1RSetUpdatingPauseTimePercent`, `-XX:SurvivorRatio`, `-XX:MaxTenuringThreshold`,
  `-XX:MaxGCPauseMillis`, …). Under ZGC these are **ignored no-ops at best and confusing/error-prone
  at worst**, and `+UseG1GC` alongside `+UseZGC` is a hard conflict. The migration is a **clean
  replacement**, not an overlay. The advisor (item 2) flags leftover G1 flags where it can detect
  them. `TODO(verify)` which of these emit warnings vs silent no-ops on the target JDK.
- **Advanced / optional (not defaulted):**
  - `-XX:SoftMaxHeapSize=<M>G` (< `-Xmx`) lets ZGC keep the heap smaller under normal load but grow to
    `-Xmx` under spikes — useful for **node density / oversell** on Victus nodes. Off by default;
    noted for the density workstream.
  - `-XX:ConcGCThreads` is largely self-tuning; **do not hand-tune** unless the harness shows
    allocation stalls. ZGC is intentionally low-knob.

**Plan-size boundary (grounded, important for the fleet).** ZGC is a **concurrent** collector: it
does GC work on background threads *alongside* the running server, so it needs a **few spare cores**.
On CPU-starved or heavily **oversold small plans (≈1–2 vCPU)** where the single tick thread already
pins the box, ZGC's concurrent phases contend for CPU and can fall behind (allocation stalls). On
those plans the stop-the-world simplicity of **G1** (or even Serial) can be the better default. So the
Wings template should key the flag set on plan size: **Generational ZGC for ≥ ~4 cores with
headroom; keep G1/Aikar for tiny/oversold plans.** `TODO` set the exact core/RAM threshold from the
pilot data.

### 2. GC advisor — boot-time check + warn on mismatch (server patch)

One small patch group, `patches/paper-server/optimizations/gc/` (GPL-3.0). Mirrors
[`06-memory.md`](06-memory.md) item 4 in structure and in the warning surface. It **only reads** JVM
state — it never sets a flag (it cannot change the collector at runtime anyway).

- **Detection.** At boot, classify the active collector from
  `ManagementFactory.getGarbageCollectorMXBeans()` names, cross-checked with
  `HotSpotDiagnosticMXBean.getVMOption(...)`:
  - **Generational ZGC** → the bean set splits into **major/minor** cycles/pauses (e.g.
    `"ZGC Major Cycles"`, `"ZGC Minor Cycles"`, `"ZGC Major Pauses"`, `"ZGC Minor Pauses"`).
  - **Non-generational ZGC** → a single ZGC cycle/pause bean set (e.g. `"ZGC Cycles"` / `"ZGC Pauses"`)
    with **no** major/minor split → this is the "ZGC but generational off" case.
  - **G1** → `"G1 Young Generation"` / `"G1 Old Generation"` (+ `"G1 Concurrent GC"`).
  - **Shenandoah / Parallel / Serial** → their respective bean names.
  Also read `getVMOption("UseZGC")` / `getVMOption("ZGenerational")` where available as a
  cross-check. `TODO(verify against target JDK)` — the exact MXBean names have shifted across JDK
  releases (especially the generational major/minor split) and may differ again on the JDK Paper 26.1
  targets.
- **Warn on mismatch.** Compare the detected collector to `optimizations.gc.profile`. If they differ
  and `warn-on-mismatch` is true, emit **one** clear startup warning: what is running, what was
  expected, and a pointer to `scripts/dev-env.sh` / the launch-flag docs. Silent when they match.
- **Warn if non-generational ZGC.** If ZGC is active but generational mode is **off** and
  `warn-if-non-generational` is true, warn that throughput is being left on the table and how to fix
  it (`-XX:+ZGenerational`, JDK-version-dependent).
- **`profile: auto`** suppresses the mismatch warning entirely (accept whatever is running) — the
  escape hatch for operators who intentionally run a non-default collector (e.g. G1 on a tiny plan per
  the boundary above), so the boundary case does not spam a warning.
- **Detect leftover G1/Aikar flags (best-effort).** Where `HotSpotDiagnosticMXBean` /
  `RuntimeMXBean.getInputArguments()` expose them, note obvious G1-only flags present while ZGC is
  active and fold that into the same one-shot warning (they are no-ops and signal a botched
  migration). Best-effort only; `TODO(verify)` which flags are observable.

This is informational-only, exactly like `gc.profile` and the memory spec's item 4. It adds **no**
per-tick cost (one read at boot) and **no** plugin-visible surface.

### 3. Metrics + lag-doctor integration (control plane)

Wires into the existing hosting metrics/doctor surface (ARCHITECTURE §5) — thin, no new game code:

- **Prometheus.** Export **GC pause distribution** (count + p50/p95/p99/max pause), **allocation
  rate**, cycle counts (major/minor for generational ZGC), and a **collector label** so the panel can
  see at a glance which collector each instance runs. Sourced from `GarbageCollectorMXBean` +
  `MemoryPoolMXBean` / GC notification listeners.
- **`/victus doctor` — `gc-profile`.** If the running collector != `gc.profile` (or ZGC is
  non-generational), surface the same message as item 2 as a doctor remediation ("switch the start
  script to Generational ZGC — this is a **launch-flag change Wings applies**, not a runtime toggle").
- **`/victus doctor` — `gc-pauses`.** If observed GC pauses correlate with MSPT spikes / missed ticks
  (a G1-on-large-heap signature), recommend the ZGC migration with the honest caveats (needs spare
  cores; validate on a pilot). Since the collector cannot change at runtime, this is a **suggest-only**
  remediation — `lag-doctor.auto-apply` never restarts the JVM with new flags on its own.

### 4. Profiles

`gc.profile` defaults to `zgc-generational` on **every** profile (the collector is behaviour-neutral,
so there is no reason for `technical`/`minigames`/etc. to differ). The **plan-size boundary** (item 1)
is orthogonal to `engine.profile` — it is enforced by the **Wings start-script template** by
core/RAM, not by the profile overlay — and an operator on a tiny plan can set `profile: auto` (or
`g1`) so the advisor stays quiet. `TODO` decide whether the Wings template auto-sets `profile: auto`
on sub-threshold plans so ZGC-vs-G1 selection and the advisor never disagree.

## victus.yml keys

`optimizations.gc.profile` already exists in `VICTUS-CONFIG.md`. This spec **pins its semantics** and
**adds** two informational sub-flags — the same additive pattern the memory spec used
(`warn-if-no-jvm-string-dedup`) and the chunks spec used (`chunks.pregen.*`). **No key here changes
the collector**; they only control the *labels and warnings*.

```yaml
optimizations:
  gc:
    # INFORMATIONAL ONLY. The collector is chosen by JVM LAUNCH FLAGS, never at runtime.
    # This is the collector Victus EXPECTS to be running under; the engine reads the ACTIVE GC at
    # boot and warns on mismatch. It does NOT and CANNOT set the collector.
    #   zgc-generational (default/recommended) | g1 | shenandoah | zgc | auto
    #   - zgc-generational : Generational ZGC (-XX:+UseZGC -XX:+ZGenerational), Java 21+  [recommended]
    #   - g1               : legacy G1 + Aikar's flags (fallback for tiny / CPU-starved / oversold plans)
    #   - zgc              : non-generational ZGC (discouraged — loses throughput vs generational)
    #   - auto             : accept whatever collector is running; suppress the mismatch warning
    profile: zgc-generational

    # Emit ONE boot warning (and a /victus doctor item) if the running collector != profile.
    # No effect when profile: auto. The engine still never changes a JVM flag.
    warn-on-mismatch: true

    # Warn once if ZGC is active but GENERATIONAL mode is OFF (throughput loss on Java 21/22 when
    # -XX:+ZGenerational was omitted). Silent under generational ZGC or a non-ZGC collector.
    warn-if-non-generational: true
```

- **Defaults & profiles.** `profile: zgc-generational` on **every** profile (§4); both warn flags
  default `true` everywhere. Any explicit key beats the profile overlay, per `VICTUS-CONFIG.md`.
- **Consistent with the top-level schema.** `optimizations.gc.profile` already appears in
  `VICTUS-CONFIG.md` (as informational); this spec pins it and adds `warn-on-mismatch` /
  `warn-if-non-generational`.
- **Related keys used, not introduced:** `engine.profile` (supplies the default),
  `optimizations.memory.*` (`UseStringDeduplication` rides the same launch line; a smaller live set
  from `memory.dedup` makes ZGC cycles cheaper — [`06-memory.md`](06-memory.md)),
  `hosting.limits.max-heap-mb` (the operator-visible heap that must leave OS/off-heap headroom),
  `hosting.metrics.prometheus.*` (where GC pause/alloc metrics land), and `hosting.lag-doctor.*`
  (the `gc-profile` / `gc-pauses` remediations; `auto-apply` never relaunches the JVM).

## Vanilla-parity & plugin-compat risks

- **GC is invisible to game logic and the plugin API — the default path is 100% compatible.** The
  collector changes *when memory is reclaimed*, never *any value, event, tick outcome, or API
  result*. There is **no** new/changed Bukkit/Spigot/Paper surface, and nothing behaviour-changing.
  The advisor is read-only. This is the strongest compat story of any Phase 1 area.
- **Timing sensitivity, not correctness.** A plugin cannot observe the collector, but any code that
  (incorrectly) depends on GC pause *timing* — e.g. a benchmark or a real-time assertion that assumed
  ~35 ms G1 hiccups — sees *smoother* behaviour, never wrong behaviour. This is strictly an
  improvement; noted only for completeness.
- **The migration is the risk, not the mechanism.** Switching the fleet default off the current
  Aikar/G1 tuning is a **real operational change** (ROADMAP known-risk #4): (a) on CPU-starved /
  oversold small plans ZGC can fall behind for want of spare cores (allocation stalls) — mitigated by
  the plan-size boundary keeping G1 on tiny plans; (b) ZGC's higher off-heap/committed-RSS footprint
  plus `AlwaysPreTouch` can trip native-OOM/OOM-killer if `-Xmx` was sized to the full box — mitigated
  by the ~1–1.5 GB OS-headroom rule; (c) raw throughput on pure CPU-bound single-thread work can dip a
  few % vs G1 (see Honest expected gain). **Mitigation: validate on a pilot node before fleet
  rollout** (a single DE-1 free node soaked on ZGC, panel MSPT p99 + alloc-stall/native-OOM logs
  watched) before flipping the Wings template default.
- **Don't mix flag sets.** Leftover G1/Aikar flags under ZGC are no-ops or conflicts; the advisor
  flags them (best-effort). A botched half-migration is the most likely operator mistake — the clean
  "replace, don't overlay" rule and the advisor exist to catch it.
- **Fail-safe.** The advisor can only *warn*; it cannot break a boot. If detection is uncertain on an
  unexpected JDK (bean names shifted), it degrades to a **soft/no-op** note rather than a false alarm.
  Worst case is a missing warning, never a broken server — the same fail-safe posture as the chunks
  and memory specs.

## Tests & verification

Per CONTRIBUTING §2 (no vanity metrics): **≥150 bots, real workloads, MSPT distribution**, identical
hardware, Paper-Aikar/G1 vs Victus-Generational-ZGC.

- **A/B GC bench (the payoff).** Same world + heap + workload on identical hardware, **G1+Aikar** vs
  **Generational ZGC**. Report: **MSPT distribution** (p50/p95/p99/max), **GC pause distribution**
  (from `-Xlog:gc*` and `GarbageCollectorMXBean`), **missed-tick count**, **allocation rate**, and
  **raw throughput** on a CPU-bound redstone/entity load. Expect: ZGC max pause **sub-ms** vs G1's
  long p99 tail; median MSPT roughly flat (possibly a few % worse under G1's throughput edge); **p99
  MSPT and missed-tick count markedly better** under ZGC.
- **Missed-tick correlation (the headline claim).** Overlay GC pause events on the per-tick time
  series and assert that ZGC **removes the pause-correlated MSPT spikes** that G1 produces (a
  ~180 ms G1 pause landing mid-tick blows ~3.6 ticks of budget at once). This is the grounded win the
  whole spec rests on — prove it, don't assume it.
- **Heap-scaling test.** Repeat across small/medium/**large** heaps. G1 pause grows with live set;
  ZGC pause stays ~constant sub-ms. Assert the ZGC advantage **widens as heap grows** (big
  modpacks / high render distance / many entities) — and cross-check the live-set reduction from
  [`06-memory.md`](06-memory.md) makes ZGC cycles cheaper.
- **CPU-headroom / oversell test (the boundary).** Run on a headroom-constrained (few-core / oversold)
  node and confirm whether ZGC falls behind (allocation stalls, rising heap). Use the result to set
  the exact **plan-size threshold** at which the Wings template keeps G1 instead of ZGC. This test
  defines a shipping default, not just a number.
- **Advisor unit tests.** Mock `GarbageCollectorMXBean` name sets for Generational-ZGC,
  non-generational-ZGC, G1, Shenandoah, Parallel, Serial and assert correct classification. Assert:
  mismatch → exactly one warning; matching → silent; `profile: auto` → silent; ZGC-non-generational →
  `warn-if-non-generational` fires; and the advisor **never** attempts to set a JVM flag.
- **OS-headroom / native-OOM test.** Size `-Xmx` too close to container RAM under ZGC+AlwaysPreTouch
  and confirm the failure mode (native-OOM/OOM-killer) to validate the ~1–1.5 GB headroom guidance;
  then confirm the headroom rule prevents it.
- **Pilot-node soak (rollout gate).** One DE-1 free node on Generational ZGC for a soak window; watch
  panel MSPT p99, GC pause metrics, alloc-stall and native-OOM logs before flipping the fleet default.
  Ties to ROADMAP risk #4.
- **Top-50 plugin suite.** GC choice is plugin-invisible, so this is a **sanity gate**: the suite must
  behave identically under ZGC and G1 (it will). Confirms the product promise holds trivially.

## Honest expected gain

**Illustrative targets, to be proven by the Phase 1 benchmark harness — not measured facts.** The
pause figures below (G1 **~35 ms avg / ~180 ms p99**, ZGC **sub-millisecond**) are **illustrative**,
labelled as such in ARCHITECTURE §3, and are **targets for the harness to confirm on Victus
hardware**, not benchmarks we have run.

- **The headline: eliminates pause-driven missed ticks.** G1's stop-the-world pauses (~35 ms avg,
  ~180 ms p99, illustrative) can exceed the 50 ms tick budget and cause visibly missed ticks /
  stutter; Generational ZGC's sub-ms pauses **never** blow a tick. So **p99 MSPT / TPS smoothness
  improves markedly**, especially on larger heaps — this is the real, defensible win.
- **Raw throughput: ~0–15% swing, workload-dependent — and G1 can edge it.** ZGC trades a little
  throughput for latency, so on **pure CPU-bound single-thread** work (the heavy vanilla tick) G1 can
  be a few % *faster* in a GC-free window. Net expectation: **median MSPT roughly flat to slightly
  worse, tail dramatically better.** The ~0–15% is a **swing in either direction**, not a promised
  gain. Illustrative; the harness decides.
- **Bigger heaps → bigger ZGC win.** G1 pause scales with live set; ZGC pause is ~constant regardless
  of heap. The larger the heap (modpacks, high view-distance, entity-dense worlds), the more G1's tail
  hurts and the more ZGC helps.
- **Needs headroom — gains shrink or invert on CPU-starved plans.** Concurrent GC needs a few spare
  cores; on ~1–2 vCPU oversold plans ZGC can lose to G1. Hence the plan-size boundary. This is a
  **caveat that shapes the default**, not fine print.
- **Memory cost, not saving.** ZGC's off-heap/mapped overhead plus `AlwaysPreTouch` mean **higher,
  flatter RSS** than G1 — budget the ~1–1.5 GB OS headroom. Node density comes from
  [`06-memory.md`](06-memory.md) (smaller live set) and optionally `SoftMaxHeapSize`, **not** from
  the collector switch.
- **~0 gameplay / API impact.** GC is invisible to plugins and game logic; the only downside is the
  operational migration risk (validate on a pilot).

Grounded in the ARCHITECTURE §3 GC row ("Default Generational ZGC — sub-ms pauses vs G1 ~35 ms avg /
~180 ms p99") and the §3 note that migrating off Aikar/G1 is deliberate and must be pilot-validated.

## Prior art / references

- **OpenJDK ZGC.** The concurrent, region-based, scalable low-latency collector — pause times in the
  sub-millisecond range **independent of heap size**; the technology this spec adopts as the default.
- **Generational ZGC (JEP 439, JDK 21).** Splits ZGC into young/old generations to recover the
  throughput single-generation ZGC gave up; enabled via `-XX:+UseZGC -XX:+ZGenerational`. Made the
  **default** for `-XX:+UseZGC` in **JDK 23 (JEP 474)**, with non-generational ZGC and the explicit
  flag deprecated. `TODO(verify)` exact behaviour on the JDK Paper 26.1 targets.
- **Aikar's flags (Daniel Ennis / PaperMC).** The G1GC tuning set this migration **replaces** as the
  Victus default — and retains as the **fallback** for tiny/CPU-starved/oversold plans and as the
  current fleet tuning (see the `game-server JVM tuning` infra memory). The `-Dusing.aikars.flags`
  marker convention comes from Paper's start script.
- **HotSpot G1GC.** The baseline collector Generational ZGC is measured against here.
- **Shenandoah (Red Hat / OpenJDK).** Alternative low-pause concurrent collector — named for context
  and accepted as a `gc.profile` value; **not** the Victus default.
- **PaperMC start-script / flag guidance.** Upstream's documented recommended flags — the baseline
  operator experience (G1 + Aikar) this spec moves off of. `TODO(verify)` whether 26.1's recommended
  flags have themselves shifted toward ZGC.
- **Sibling specs.** [`06-memory.md`](06-memory.md) (`UseStringDeduplication` on the same launch line;
  live-set reduction that makes ZGC cycles cheaper; the identical informational-flag-check pattern) and
  ARCHITECTURE §5 / [`../../design/modules/lag-doctor.md`](../../design/modules/lag-doctor.md) (the
  metrics + doctor surface the advisor plugs into).
