# Phase 4 — P4.1 audit: what Paper 26.2 / Moonrise already give us for tick threading

**Scope:** in-tree audit (reliable, code-grounded) of the threading/region primitives present in the
Victus fork today, to size the `PARALLEL`/`REGIONIZED` work in `01-regionized-threading-plan.md`.

## Findings (measured from the source, 2026-07-23)

1. **The server tick is a single serial loop.** `MinecraftServer.tickServer` (and every phase around it)
   iterates `getAllLevels()` **sequentially** — worlds tick one after another on one thread. This is the
   unmodified Paper/vanilla baseline; nothing ticks in parallel today.

2. **Moonrise chunk system is present (~125 source files).** The threaded chunk generation / IO / loading
   system is in-tree (it's what async chunk send + the chunk-worker/IO auto-uncap already build on). It also
   carries the region-of-chunks notion via `ThreadedTicketLevelPropagator.SECTION_SHIFT`
   (`TickRegions.getRegionChunkShift()`), and `ca.spottedleaf.concurrentutil` ships as a **dependency jar**
   (0 source files) — Spottedleaf's lock-free/concurrency primitives are available at runtime.
   → Foundation for **chunk-side** concurrency, not tick regionization.

3. **The Folia scheduler API is fully present, with a main-thread fallback.**
   `RegionScheduler` / `GlobalRegionScheduler` / `AsyncScheduler` / `EntityScheduler` exist, and
   `FallbackRegionScheduler` simply delegates region-scheduled tasks to the global (main-thread) scheduler.
   → **A plugin written "Folia-aware" (using `entity.getScheduler()`, `server.getRegionScheduler()`, etc.)
   runs correctly on Victus TODAY** on the main-thread fallback, and would keep working under a future
   `REGIONIZED` tier where the fallback becomes real regions. This is the portability bridge.

4. **Folia's regionized-ticking ENGINE is absent.** Zero `ThreadedRegionizer` / `RegionizedServer` class
   definitions; `io.papermc.paper.threadedregions.TickRegions` is literally a `// placeholder class for Folia`
   stub. → Regionized *ticking* is not scaffolded; it remains the from-scratch/merge effort that doc 01's
   approaches (1) merge-Folia / (2) reimplement-on-Moonrise / (3) Folia-backed-lobby-type describe.

## What this changes in the plan

- **`PARALLEL` and `REGIONIZED` tick engines are genuine builds** — Moonrise gives us the threaded chunk
  system + concurrency utils + a region-chunk-shift constant, but **not** parallel/regionized world ticking.
  Doc 01's sequencing and approach analysis stand unchanged.
- **New, low-risk step we can take NOW (P4.0), before any threading engine exists:**
  **migrate Victus's own plugins to the Folia scheduler API.** Because the fallback runs on the main thread,
  adopting `getScheduler()`/`getRegionScheduler()`/`getAsyncScheduler()` in VictusPlugin, VictusHub,
  VictusDiscovery, VictusWaiter, etc. is **zero-cost on `SINGLE`/`PARALLEL`** and makes them
  **regionized-ready** the day `REGIONIZED` lands — exactly the ROADMAP mitigation ("ship our own
  hub/lobby plugins as Folia-aware"), doable with no engine work and no compat risk. This is the highest-
  value immediate move and the recommended next action.

## Still-open question (needs web/ecosystem input, not code)

Does a **Folia build track MC 26.2** closely enough today for doc-01 approach (1)/(3) (Folia-backed lobby
type behind Velocity)? This is post-training-cutoff and depends on the live Folia release cadence for 26.2 —
best answered from current Folia release channels / the owner's ecosystem knowledge rather than guessed.
If it lags, approach (2) (reimplement on Moonrise) or deferring `REGIONIZED` until Folia catches up become
the live options; `PARALLEL` (compat-safe, no Folia dependency) is unaffected and can proceed regardless.

## Recommended order after this audit
1. **P4.0 (now, low-risk):** adopt the Folia scheduler API in Victus's own plugins → regionized-ready, zero cost today.
2. **P4.1 (next big build):** `PARALLEL` multi-world ticking (compat-safe, no Folia dependency) — doc 01 §Step A.
3. **P4.x:** resolve the Folia-26.2 landscape question, then pursue `REGIONIZED` via the recommended lobby-type split.
